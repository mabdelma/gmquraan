# Example — second instance on the Qarrito VPS

This codebase now has two homes. `origin` is
`github.com/mabdelma/example` (private); the previous Unskinned
remote is kept as `app` so nothing is lost. On the VPS the two deployments sit
side by side and share nothing but the machine and the edge proxy:

| | app | Example |
|---|---|---|
| Folder | `/var/www/app` | `/var/www/app` |
| Compose project | `-p app` | `-p tenant` |
| Compose file | `infra/compose/docker-compose.prod.yml` | `infra/compose/docker-compose.tenant.yml` |
| Containers | `app-*` | `app-*` |
| Internal network | `app_app_internal` | `tenant_tenant_internal` |
| Volumes | `app_pgdata`, `app_uploads`, `app_documents` | `tenant_pgdata`, `tenant_uploads`, `tenant_documents` |
| Database | `app` on `app-postgres` | `tenant` on `app-postgres` |
| Env | `/var/www/app/.env` | `/var/www/app/.env` |
| Host port | none | `3600` → `app-web:3000` |
| Domain | `example.com` | `tenant.example` |

Public traffic reaches both through the shared Caddy
(`vps-prod-caddy-1`) on the external `edge` network. The one host port above
is Example's direct-access door; nothing else on the box listens on 3600.


**`/var/www/app` is untouched by any of this.** The Example stack was created
alongside it, not from it.

## Bringing Example up

Steps 1, 4, 5 and 6 have been run: `.env` exists with generated secrets, all ten
containers are built and up, and both databases carry their schema. What is
**not** done is step 2 (DNS still points at the Tasjeel parking IP) and
therefore step 3 (no Caddy vhost, no certificate). Until DNS moves, the stack is
reachable only on port 3600, over plain HTTP.

### 1. Fill in the env

```sh
cd /var/www/app
cp .env.tenant.example .env
openssl rand -base64 48    # → AUTH_SECRET
openssl rand -base64 32    # → POSTGRES_PASSWORD
$EDITOR .env               # APP_URL/PORTAL_URL are pre-filled with tenant.example
```

`AUTH_SECRET`, `POSTGRES_PASSWORD`, `APP_URL` and `PORTAL_URL` are declared with
`:?` in the compose file, so a missing one stops the stack from starting instead
of quietly bringing it up on the wrong domain.

### 2. DNS — `tenant.example`

The domain runs on Tasjeel's own nameservers (`ns5.tasjeel.ae`, `ns6.tasjeel.ae`),
so the records are edited in the Tasjeel control panel, not at a third-party DNS
host. As of 2026-08-14 the apex and `www` point at `203.0.113.20` (a Tasjeel
parking host serving an empty `Index of /`), and no other subdomain resolves.

There is also an `MX 0 tenant.example` — mail for the domain is delivered to
whatever the apex A record points at. **That makes the web and mail changes one
change, not two:** the moment the apex moves to the VPS, mail for the domain
follows it to a mailcow that does not host `tenant.example` and every message
bounces. Set the MX in the same edit.

#### Web

| Type | Name | Value | TTL | Note |
|---|---|---|---|---|
| A | `@` | `203.0.113.10` | 3600 | replaces `203.0.113.20` |
| A | `www` | `203.0.113.10` | 3600 | replaces `203.0.113.20`; Caddy 301s it to the apex |
| A | `central` | `203.0.113.10` | 3600 | admin console |
| A | `ai` | `203.0.113.10` | 3600 | AI advisor |
| A | `api` | `203.0.113.10` | 3600 | public API |
| A | `workforce` | `203.0.113.10` | 3600 | team portal |
| CAA | `@` | `0 issue "letsencrypt.org"` | 3600 | optional; stops any other CA issuing for the domain |

Add only the subdomains you want live — each one has a vhost in
`infra/gateway/example.caddy`, and a host that resolves but has no vhost gets
Caddy's default response rather than the app.

#### Mail — mailcow on the same VPS

mailcow already runs on this box (`MAILCOW_HOSTNAME=mail.partner-three.example`).
`tenant.example` is now its fifth domain — **the server side is done**:

- domain `tenant.example` added and active (10 mailboxes, 1 GB default quota)
- mailbox `postmaster@tenant.example` created and active
- DKIM key generated, selector `dkim`, 2048-bit
- `mail.tenant.example` appended to `ADDITIONAL_SAN` in `mailcow.conf`
  (backup alongside it), acme container restarted

What is left is the DNS below. The acme run confirmed the state honestly: it
logged `No A or AAAA record found for hostname mail.tenant.example` and skipped
it, leaving the existing certificates untouched — `neither changed nor due for
renewal`. It then sleeps for a day, so once the records exist, either wait for
the next run or force it with
`cd /var/www/mailcow && docker compose restart acme-mailcow`.

| Type | Name | Value | TTL | Note |
|---|---|---|---|---|
| A | `mail` | `203.0.113.10` | 3600 | the mail host itself |
| MX | `@` | `10 mail.tenant.example` | 3600 | **replaces the existing `0 tenant.example`** |
| TXT | `@` | `v=spf1 mx a:mail.tenant.example -all` | 3600 | SPF: only this host may send as the domain |
| TXT | `dkim._domainkey` | *generated by mailcow* | 3600 | mailcow → Configuration → ARC/DKIM → add key for the domain, selector `dkim`, 2048-bit, then copy the record it prints |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:postmaster@tenant.example` | 3600 | start at `p=none`, tighten to `quarantine` once reports look clean |
| CNAME | `autodiscover` | `mail.tenant.example` | 3600 | optional, Outlook autoconfiguration |
| CNAME | `autoconfig` | `mail.tenant.example` | 3600 | optional, Thunderbird autoconfiguration |

Two deliverability notes. The reverse DNS for `203.0.113.10` resolves to
mailcow's own hostname, not `mail.tenant.example`; that is fine — outbound mail
HELOs as `mail.partner-three.example` and SPF still passes on the IP, which is why the
record above uses `a:` rather than a bare `ip4:`. And add `mail.tenant.example` to
mailcow's `ADDITIONAL_SAN` so it gets a certificate under its own name for
IMAP/SMTP clients.

**If mail is staying at Tasjeel** instead: create `mail` as an A record pointing
at `203.0.113.20` (the current host) and set the MX to `10 mail.tenant.example`.
Same shape, different IP — the point is that the MX must stop resolving through
the apex before the apex moves.

#### Order and verification

DNS first, Caddy second: issuance is an HTTP-01 challenge and fails against a
host that does not resolve here. Tasjeel quotes 12–24h to propagate, though it
is usually minutes.

```sh
dig +short tenant.example            # → 203.0.113.10
dig +short MX tenant.example         # → 10 mail.tenant.example
dig +short TXT tenant.example        # → v=spf1 ...
```

### 3. Caddy

Append `infra/gateway/example.caddy` to
`/var/www/gateway/infrastructure/caddy/Caddyfile`, then:

```sh
docker exec vps-prod-caddy-1 caddy validate --config /etc/caddy/Caddyfile
docker exec vps-prod-caddy-1 caddy reload  --config /etc/caddy/Caddyfile
```

### 4. Build and start

Ten images. Check free disk first — the app stack's images are already on this
box and this roughly doubles them.

```sh
df -h /
cd /var/www/app
docker compose -f infra/compose/docker-compose.tenant.yml --env-file .env -p tenant up -d --build
```

### 5. Create the schema — manual, as in app

Nothing applies the schema for you; the Dockerfile runs `prisma generate` only.
On a brand-new empty database `db push` is safe (there is nothing to drop), but
follow the same rule afterwards as the app stack — see the honesty notes in
[DEPLOY.md](../DEPLOY.md).

There are **two** databases, as in app: the tenant datamodel in `tenant`, and the
control plane in `tenant_control` from its own `control.prisma`. Postgres only
creates the first from `POSTGRES_DB`, so the control one has to be created by
hand before its schema can be pushed — miss it and the workforce portal's tenant
lookup fails at runtime rather than at deploy time.

```sh
docker exec app-postgres psql -U tenant -d tenant -c "CREATE DATABASE tenant_control;"
docker exec app-web npx prisma db push --schema=/repo/packages/db/prisma/schema.prisma  --skip-generate
docker exec app-web npx prisma db push --schema=/repo/packages/db/prisma/control.prisma --skip-generate
bash backup.sh    # after the schema change, not only before
```

That gives 84 tables in `tenant` and 5 in `tenant_control`, matching the app stack.

### 6. Verify

```sh
docker compose -p tenant ps
curl -I https://tenant.example
```

## Updating later

The VPS clone pulls from GitHub with its own deploy key (`~/.ssh/example_deploy`
on the VPS, host alias `github-example`), so:

```sh
cd /var/www/app && git pull
docker compose -f infra/compose/docker-compose.tenant.yml --env-file .env -p tenant up -d --build
# if schema.prisma changed: backup, review the diff, db push, backup again
```
