# 1. Tenant isolation

**Status:** accepted, 11 August 2026
**Decision:** one Postgres schema per tenant, on a shared instance, with the
connection string carrying the boundary. A dedicated database per tenant is the
same code with a different URL, offered where a customer requires it.

## The problem

GM-OS was written for one company. Seventy models, several hundred queries, and
not one of them mentions a tenant. Selling it to other companies means every one
of those queries has to become incapable of returning another customer's rows.

What it holds raises the stakes: controlled documents, employment records, pay,
right-to-work evidence, records under legal hold. A leak between two customers
is not a bug report, it is a notifiable incident for both of them.

## Options

**Row-level — one set of tables, a `tenantId` column, Postgres RLS.**
Cheapest to operate. Every existing query has to gain a filter, and every future
one has to remember. Prisma client extensions can inject the filter
automatically, and RLS enforces it in the database so a forgotten `where` fails
closed rather than leaking. That combination is genuinely strong.

It is still the option where correctness is a property of *every query* rather
than of the connection. `$queryRaw`, aggregates and nested writes each need
their own reasoning. With 70 models already written tenant-blind, the retrofit
is the largest and least verifiable piece of work of the three.

**Schema per tenant — one database, one Postgres schema each.**
The connection carries the boundary: `?schema=t_acme`. A query cannot name
another tenant's rows because they are not on its `search_path`. None of the
existing queries change. Per-tenant backup is `pg_dump -n`, and per-tenant
restore does not touch anybody else — which matters for a records system with
retention rules and legal hold.

Cost: a Prisma client per tenant, so connection pools multiply, and migrations
run once per schema.

**Database per tenant.**
Strongest, and what a regulated buyer will ask for. Heaviest to operate: N
databases to migrate, monitor and back up.

## Why schema per tenant

Isolation should be a property of the connection, not a property of every
developer's memory. That is the whole argument. The other two differ from it
only in operational weight.

It also happens to be the option that does not require rewriting code that
already works and is already covered by 321 tests. Row-level would touch all of
it, and the retrofit would be the most likely source of exactly the defect it
was meant to prevent.

The escape hatch is cheap: a customer who requires their own database gets one
by changing a connection string, because the code already treats the connection
as the boundary. Nothing else changes.

## Consequences

**The control plane is separate.** Tenants, subscriptions, provisioning state
and billing live in their own schema with their own Prisma client. Tenant data
and the record of who the tenants are never share a query.

**Clients are cached, not created per request.** A Prisma client per tenant
holds a pool. An LRU with a bounded size and a connection pooler in front of
Postgres, or a busy instance exhausts `max_connections` and every tenant fails
at once. This is the failure mode to watch, and the reason to keep the cache
size and the pooler configuration together in one place.

**Migrations become a fan-out.** `db push` runs per schema. It must be
idempotent, it must be ordered, and a partial failure has to be visible per
tenant rather than as one aggregate error. A tenant left a version behind is
worse than one that failed loudly.

**Nothing may derive a schema name from user input.** The schema name is
generated by the control plane and stored; it is never built from a subdomain or
a form field. A schema name reaching SQL from a request is the one way this
model leaks.

**Restore is per tenant and that is a feature.** It should be exposed as one,
because "restore our data without touching anybody else's" is what a buyer of a
records system asks about.
